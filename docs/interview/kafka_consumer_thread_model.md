## 📊 Kafka Consumer 线程模型演进

### 旧版客户端（0.10.0 之前）：心跳在主线程

```
┌──────────────────┐
│ 主线程（单线程）  │
├──────────────────┤
│                  │
│ 1. poll() 获取   │
│    消息          │
│                  │
│ 2. 处理消息      │
│    (40 秒) ❌     │  ← 阻塞期间无法发送心跳
│                  │     → session.timeout.ms 超时
│ 3. 发送心跳 ❌    │
│                  │
└──────────────────┘
```

**问题**：处理消息时无法发送心跳 → `session.timeout.ms` 超时

### 新版客户端（0.10.1+）：心跳独立线程

```
┌──────────────────────────────────────────┐
│  Kafka Consumer                          │
├──────────────────────────────────────────┤
│                                          │
│  ┌──────────────┐  ┌─────────────────┐  │
│  │ 主线程        │  │ 心跳线程（后台） │  │
│  │              │  │                 │  │
│  │ 1. poll()    │  │ 自动发送心跳     │  │
│  │    获取消息  │  │                 │  │
│  │              │  │ 独立运行！       │  │
│  │ 2. 处理消息  │  │ ✅ 不受主线程    │  │
│  │    (40 秒)   │  │    影响！        │  │
│  │              │  │                 │  │
│  │ 3. 下一次    │  │ ✅ 继续发送      │  │
│  │    poll() ❌ │  │    心跳！        │  │
│  │    没调用    │  │                 │  │
│  │    （被阻塞） │  │                 │  │
│  └──────────────┘  └─────────────────┘  │
│         ↓                                 │
│   超过 max.poll.interval.ms               │
│         ↓                                 │
│  Broker: "处理太慢，Livelock！"            │
└──────────────────────────────────────────┘
```

**关键变化**：
- 心跳线程独立运行，不受主线程影响
- 即使主线程在处理消息，心跳仍然会发送
- **新问题**：主线程迟迟不调用 `poll()`，Broker 判定为 Livelock

## 🔍 两个超时参数的区别

### 参数 1：session.timeout.ms

**作用**：控制 Consumer 发送心跳的最大间隔

**谁负责**：**心跳线程**（后台自动发送）

**超时后果**：Broker 认为 Consumer **死了**（Dead）

**典型场景**：
- 进程崩溃
- 网络分区
- 机器宕机

**默认值**：10 秒（0.10.1+ 版本）

**配置建议**：
```properties
# 应该 > heartbeat.interval.ms 的 3 倍
session.timeout.ms=30000        # 30 秒
heartbeat.interval.ms=10000     # 10 秒（心跳频率）
```

---

### 参数 2：max.poll.interval.ms

**作用**：控制**两次 `poll()` 调用之间的最大时间间隔**

**谁负责**：**主线程**（必须及时调用 `poll()`）

**超时后果**：Broker 认为 Consumer **Livelock**（活着但无法正常工作）

**典型场景**：
- 主线程处理消息太慢
- GC 停顿时间过长
- 无限循环或死锁
- **本次故障：大文件处理耗时 40 秒**

**默认值**：5 分钟（300000 ms）

**配置建议**：
```properties
# 应该 ≥ 单条消息的最大处理时间
max.poll.interval.ms=600000     # 10 分钟

# 如果你的任务可能耗时很长，必须增大这个值！
```

## 📝 记忆要点（面试背诵）

### 关键词
1. **线程分离**：心跳线程 vs 处理线程
2. **Livelock**：进程活着但无法工作
3. **两个超时**：
   - `session.timeout.ms`：心跳超时（进程死了）
   - `max.poll.interval.ms`：Poll 间隔超时（活锁）
4. **核心参数**：`max.poll.interval.ms` 必须 ≥ 最大任务处理时间

### 面试话术模板

"在现代 Kafka 客户端中（0.10.1+），心跳由后台线程自动发送，即使主线程在处理消息，心跳仍然会正常发送。所以 `session.timeout.ms` 不是问题的根本原因。真正的问题是 **`max.poll.interval.ms`**——主线程处理大文件太久，没有及时调用下一次 `poll()`，Broker 判定为 **Livelock**，主动将其踢出消费组。"

## 🔥 为什么这个修改如此重要？

### 1. 证明你真的理解 Kafka

大多数候选人只知道 `session.timeout.ms`，不知道 `max.poll.interval.ms`。

你能区分这两个参数，说明：
- ✅ 读过 Kafka 官方文档
- ✅ 有真实故障排查经验
- ✅ 理解 Kafka Consumer 的线程模型

### 2. 证明你有工程思维

肤浅的回答只会"增大超时时间"，但：
- 增大到多少？为什么？
- 两个参数有什么区别？
- 增大一个够吗？还是两个都要调？

深度回答（v2.1）：
- 核心是 `max.poll.interval.ms`
- `session.timeout.ms` 是辅助（防止网络抖动）
- 两者关系：`session.timeout.ms < heartbeat.interval.ms * 3 < max.poll.interval.ms`

### 3. 证明你能应对"压力追问"

**面试官可能的追问**：
- "如果心跳是后台线程发送的，那为什么还会重平衡？"
- "Livelock 和 Deadlock 有什么区别？"
- "如果任务处理时间不确定（有时 1 秒，有时 10 分钟），怎么配置？"
