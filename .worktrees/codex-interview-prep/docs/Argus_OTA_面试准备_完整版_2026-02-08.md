## 2. 项目流程介绍

## 2.1 架构全景图

```text
车端/客户端
  -> Ingestor (Go/Gin)
  -> MinIO 对象存储
  -> Kafka (batch-events)
  -> Orchestrator (Go)
     -> 任务分发/状态编排
     -> Redis Barrier 进度协同
  -> Kafka (gathering-completed / diagnosis-completed)
  -> AI Worker (Go + Eino + RAG)
  -> PostgreSQL / pgvector
  -> Query Service (Singleflight + Redis Cache)
```

## 2.2 五阶段数据流（可画图）

### 阶段 1：上传接入

- 客户端创建批次：`POST /api/v1/batches`
- 上传文件：`POST /api/v1/batches/:id/files`
- 完成上传：`POST /api/v1/batches/:id/complete`
- 文件流写入 MinIO，并记录文件元数据到 PostgreSQL

### 阶段 2：事件编排

- 批次状态变更事件写入 Kafka。
- Orchestrator 消费事件并推进状态机：`pending -> uploaded -> scattering ...`

### 阶段 3：并行处理与屏障

- Worker（当前仓库是 mock worker）处理文件并发布 `FileParsed`。
- Orchestrator 使用 Redis Set 计数：`SADD + SCARD`。
- 达到总文件数后进入下一阶段，未达到则持续等待。

### 阶段 4：AI 诊断（Eino）

- AI Worker 消费聚合完成事件。
- 执行 Eino Graph：`hard_guards -> data_loader -> confidence -> rag/llm`。
- 低置信度走 RAG 检索，高置信度走快速 LLM 路径。

### 阶段 5：结果查询

- Query Service 提供报告与进度接口。
- 先查 Redis，miss 后查 PostgreSQL，回填缓存。
- Singleflight 合并同 batch 并发请求。

## 2.3 核心模块职责

### Ingestor

- HTTP 接入、批次创建、文件上传、状态触发。

### Orchestrator

- 消费 Kafka、推进状态机、处理 FileParsed/GatheringCompleted/DiagnosisCompleted。
- 补偿任务扫描卡住批次。

### AI Worker（Eino）

- 数据加载、置信度计算、RAG 检索、LLM 输出。
- 检索失败时显式降级，保证链路不中断。

### Query Service

- 报告查询与进度查询。
- 缓存 + Singleflight 防止 DB 瞬时抖动。

## 4. 核心技术详解

## 4.1 Redis Barrier 分布式屏障

### A 层（当前可说已落地）

当前实现采用 Redis Set 幂等计数：

```go
key := fmt.Sprintf("batch:%s:processed_files", batchID)
added, _ := redis.SADD(ctx, key, fileID)
if added > 0 {
    redis.EXPIRE(ctx, key, 24*time.Hour)
}
count, _ := redis.SCARD(ctx, key)
if count == int64(batch.TotalFiles) {
    // 触发下一阶段
}
```

**你可以这样回答**：
- 为什么不是简单 `INCR`：因为重复消费会超计数。
- 为什么是 Set：天然去重，幂等逻辑更直接。
- 如何兜底：补偿任务定时扫描卡住状态。

### B 层（增强方案，保留你原稿）

可升级为 Lua 原子脚本（`SISMEMBER + SADD + INCR + 判断`），把多操作收敛到一条原子命令，进一步减少竞态窗口。

### A 层（当前仓库事实）

- 当前上传入口使用 multipart 表单读取文件流并写入 MinIO。
- 可讲“流式传输与大文件稳定性”。

### B 层（你原稿保留）

## 4.4 Singleflight 防缓存击穿

```go
var sf singleflight.Group

v, err, shared := sf.Do(batchID, func() (interface{}, error) {
    if cached := redis.Get(key); cached != nil {
        return cached, nil
    }
    report := db.Query(batchID)
    redis.Set(key, report, 10*time.Minute)
    return report, nil
})
```

面试要点：
- 同一 key 并发只执行一次。
- 其余请求共享结果，避免缓存过期瞬间 DB 被打满。
- 可补充 panic recover + 超时控制作为防御性增强。

## 4.5 Kafka 可靠性设计

### Producer 侧

- `acks=all`
- `idempotent=true`
- retry + backoff

### Consumer 侧

- 处理成功才 mark/commit。
- 处理失败不提交，允许重试（至少一次语义）。

### 你可以讲的“可靠性链路”

- 发送可靠：acks + 幂等 + 重试。
- 存储可靠：副本与 ISR 策略。
- 消费可靠：手动提交 + 业务幂等。

## 4.6 Kafka Rebalance 深挖（保留你原稿）

### 现象模板

- consumer lag 暴涨
- 日志频繁出现 rebalance
- 处理线程阻塞导致 poll 间隔超时

### 根因模板

- 长任务阻塞消费线程，超过 `max.poll.interval.ms`。

### 修复模板

1. 增大 `max.poll.interval.ms`
2. 减少单次处理量
3. 业务处理异步化
4. 增加 rebalance 与 lag 监控

### GMP 调度

- 大对象分配会拉高 GC 成本。

## 4.9 技术选型 trade-off（完整版）

### Redis vs Etcd（屏障场景）

- Redis：吞吐高、数据结构丰富（Set 去重好用）。
- Etcd：强一致好，但吞吐低且运维成本高。
- 当前场景：高并发进度计数优先，选 Redis 更合适。

### Eino vs LangChain

- Eino：Go 栈一致、类型安全、图编排更工程化。
- LangChain：生态更广，原型速度快。
- 当前后端主栈是 Go，选择 Eino 更稳。

### Kafka vs HTTP 直连

- Kafka：解耦、削峰、可回放。
- HTTP：简单但耦合强、抗峰值能力弱。

## 6. 压力追问题库（高频陷阱）

### Q1：`INCR + 判断 + 发 Kafka` 不是原子，怎么保证？

答法：
- 当前实现采用 Set 去重，不是单纯 INCR。
- 可升级 Lua 脚本原子化。
- 数据库唯一约束与补偿任务做兜底。

### Q2：Redis 挂了怎么办？

答法：
- 先降级策略（可切 DB/本地队列，视业务可接受度）。
- 业务不阻断优先，最终一致性由补偿保证。
- 告警与人工干预机制要明确。

### Q3：为什么零拷贝能降低 GC？

答法：
- 减少用户态大 `[]byte` 分配。
- 堆对象减少，GC 标记压力下降。

### Q4：RAG 成本怎么降？

答法：
- 上下文截断
- 动态思维链
- 语义缓存
- 小模型优先、难题再升级大模型

### Q5：Golden Dataset 怎么来？

答法：
- 从历史工单抽取“输入-结论”对。
- 最少先有一批可回放样本，再谈 F1 改善。

### Q6：Singleflight 的唯一执行 panic 了怎么办？

答法：
- recover + forget key
- 上下文超时
- 降级返回兜底值

### Q7：流量扩大 100 倍怎么办？

答法模板：
- 接入层：对象存储带宽扩容
- 编排层：Kafka partition + broker 扩容
- 计算层：worker HPA
- 存储层：读写分离/分片
- AI 层：缓存命中率与模型分级

## 7. 面试话术模板

## 7.1 1分钟开场版

这是一个分布式 OTA 日志分析与智能诊断平台。我负责事件驱动编排、查询高并发优化和 AI 诊断链路。编排侧通过 Kafka 解耦流程，Redis 屏障保证并行任务进度协同；查询侧通过 Singleflight 防止缓存击穿；AI 侧基于 Eino Graph 做置信度路由与 RAG 降级，形成可扩展的诊断流水线。

## 7.2 3分钟项目版

我们把系统拆成接入、编排、诊断、查询四层。接入层负责批次与文件上传，编排层消费 Kafka 推进状态，文件解析结果通过 Redis Set 屏障做幂等计数；诊断层是 Eino Graph，先做 guards，再算 confidence，低置信度走 RAG，检索失败显式降级；查询层通过 Redis 缓存 + Singleflight 抗并发。这个架构的核心不是“某个组件多先进”，而是链路在高并发和异常场景下仍可控、可恢复、可演进。

## 7.3 5分钟深挖版

从设计上看，我重点做了三件事。第一是把同步耦合改成 Kafka 事件驱动，降低上下游依赖，让扩容和故障隔离更容易。第二是通过 Redis 屏障与补偿任务保证批次进度最终一致，即使出现重复消息或阶段事件缺失，状态也能被纠正。第三是把 AI 诊断从“直接调模型”升级成 Eino 图编排：硬约束检查、置信度决策、RAG 检索和降级处理，保证在知识库抖动时系统还能给出受控输出。整体上我更关注工程可用性而不是单点算法效果。
