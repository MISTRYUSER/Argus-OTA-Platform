## 1. 你现在可以直接用的简历写法（已对齐仓库）

### 1.1 一句话版本（保守真实版）

基于 Go 构建分布式 OTA 日志分析平台，采用 Kafka 事件驱动解耦流程，使用 Redis 集合计数实现批次处理屏障，引入 Eino Graph + pgvector 的 RAG 诊断链路，并通过 Singleflight 解决报告查询缓存击穿问题。

### 1.2 简历项目经历（推荐）

**Argus OTA Platform（后端 / AI Agent）**

- 设计并实现 **事件驱动处理链路**：上传服务发布批次事件，编排服务消费事件并驱动后续流程，降低服务间耦合。
- 实现 **分布式批次进度屏障**：基于 Redis `SADD/SCARD` 完成文件级幂等计数与进度推进，支持补偿任务处理卡住批次。
- 实现 **查询侧高并发保护**：在 Query Service 中接入 `singleflight.Group` 合并同 Key 并发请求，避免缓存失效瞬时打满数据库。
- 基于 **Eino Graph** 落地 AI 诊断流程：`hard_guards -> data_loader -> confidence -> rag/llm`，支持低置信度自动走 RAG、RAG 异常降级。
- 实现 **RAG 混合检索**：接入 embedding + pgvector 检索，结合错误码过滤返回 TopK 相似案例，提升诊断可解释性与可复用性。

## 2. 项目流程介绍（按仓库现状）

## 2.1 端到端主流程

```text
车端/客户端
  -> Ingestor API
     1) POST /api/v1/batches 创建批次
     2) POST /api/v1/batches/:id/files 上传文件到 MinIO
     3) POST /api/v1/batches/:id/complete 触发状态变更
  -> Kafka(batch-events)
  -> Orchestrator 消费事件
     - BatchCreated: 进入 scattering
     - FileParsed: Redis Set 屏障计数
     - GatheringCompleted: 进入 diagnosing
     - DiagnosisCompleted: 进入 completed
  -> Query Service
     - GET /api/v1/batches/:id/report（Singleflight + Redis 缓存）
     - GET /api/v1/batches/:id/progress
```

## 2.2 AI Agent 流程（Eino）

```text
Kafka(gathering-completed)
  -> AI Worker
     -> Eino Graph
        hard_guards
          -> data_loader
          -> confidence
             -> (low confidence) rag -> llm
             -> (high confidence) llm
  -> Kafka(diagnosis-completed)
```

## 3.2 高频问答模板（可直接背）

### Q1：你为什么用 Kafka 而不是服务间直连 HTTP？

答：
- 这个链路是异步处理，核心需求是解耦、削峰和可重试。
- Ingestor 只负责发事件，不感知下游 Worker 规模。
- Consumer 出错时不提交 offset，消息可以重试，保证最终处理完成。

### Q2：你的分布式屏障怎么保证幂等？

答：
- 我用的是 Redis Set 屏障，不是简单计数器。
- 每个文件完成时执行 `SADD(batch:processed_files, file_id)`，天然去重。
- 再通过 `SCARD` 获取唯一完成数，与 `total_files` 比较推进状态。
- 这样重复消息不会重复计数。

### Q3：Singleflight 在你项目里解决了什么问题？

答：
- 热点报告缓存失效时，同一个 `batch_id` 会有大量并发请求同时查库。
- `singleflight.Do(key)` 把并发请求合并为一次执行。
- 首个请求查 DB 并回填缓存，其余请求共享结果，避免瞬时击穿。

### Q4：你在 AI 侧为什么选 Eino？

答：
- 后端主栈是 Go，Eino 可直接融入现有工程，类型安全更好。
- 我们需要图编排而不是单链路，Eino Graph 可以做条件路由。
- 当前链路里就是按置信度分支：低置信度走 RAG，高置信度走直出。

### Q5：RAG 失败时系统会怎样？

答：
- RAG 节点失败不会直接中断。
- 会设置 `RAGUnavailable=true`，并继续进入 LLM 节点。
- Prompt 会显式提示“知识库不可用”，避免模型误把失败当作“没有案例”。

## 6.2 Kafka 消费语义

- 处理成功才 `MarkMessage/CommitMessages`。
- 处理失败不提交 offset，可重试。
- 业务层配合幂等去重避免重复副作用。

## 6.3 Eino Graph 路由策略

- 先 hard guards 做硬约束检查。
- confidence 节点计算置信度。
- 低置信度走 RAG（慢而准），高置信度走直出（快）。
- 这是“快慢路径”思想，适合面试讲 trade-off。
